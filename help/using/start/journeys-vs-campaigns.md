# ジャーニーと施策：適切なアプローチの選定 {#journeys-vs-campaigns}

[!DNL Adobe Journey Optimizer]では、顧客にリーチしてエンゲージするための主な2つの方法が用意されています：**キャンペーン**&#x200B;と&#x200B;**ジャーニー**。 ジャーニーは、顧客の行動にもとづいてリアルタイムでマルチステップのオーケストレーションが可能なように設計されています。一方、施策は、定義されたオーディエンスに対する1回限りの放送またはスケジュール型の放送に適しています。 キャンペーンを決定したら、ユースケースに最適なキャンペーンタイプを選択できます。

このガイドでは、実行スタイル、データのニーズ、ユースケースなどにもとづいて、比較、意思決定ツリー、具体的な例を紹介し、選択するのに役立ちます。

## クイック比較の概要 {#quick-overview}

| アプローチ | 主な用途 | 実行スタイル |
|----------|----------|-----------------|
| **ジャーニー** | 条件付きロジックを利用したマルチステップのリアルタイム顧客体験 | 1:1 オーケストレーション – 各プロファイルのペース |
| **アクションキャンペーン** | オーディエンスへの定期または定期的な配信 | バッチ実行 – 送信時に一緒に処理されるオーディエンス |
| **API トリガーのキャンペーン** | 外部システムからのイベント駆動型またはトランザクションメッセージ | オンデマンド実行 – ペイロードを使用したAPI呼び出しによってトリガー |
| **キャンペーンのオーケストレーション** | 複数のエンティティをセグメンテーションする複雑なバッチワークフロー | バッチキャンバス – すべてのプロファイルをまとめて処理 |

>[!TIP]
>
>**経験則：** リアルタイム ロジックを使用して、各顧客が自分のペースで移動する必要がありますか？ **ジャーニー**&#x200B;を使用します。 スケジュールに従ってメッセージをオーディエンスに送信する？ **アクションキャンペーン**&#x200B;を使用します。 API経由で外部システムからトリガーする場合、 **API トリガーのキャンペーン**&#x200B;を使用します。 複数のエンティティのデータ、正確な数、またはバッチキャンバスが必要ですか？ **オーケストレーションされたキャンペーン**&#x200B;を使用します。

## 詳細比較 {#detailed-comparison}

この包括的な表を使用して、主な違いを理解します。

| 機能 | ジャーニー | アクションキャンペーン | API トリガーによるキャンペーン | キャンペーンの編成 |
|---------|----------|------------------|------------------------|----------------------|
| **プライマリの目的** | リアルタイム顧客コンテキストを使用したマルチステップ 1:1 オーケストレーション | オーディエンスへの1回限りまたは定期的なメッセージ配信 | 外部システムによって開始された、トランザクションメッセージまたはイベント駆動型メッセージ | 複雑なセグメンテーションワークフローを備えたマルチステップのバッチキャンペーン |
| **キャンバスの種類** | 1:1 キャンバス – 各プロファイルは自分のペースで移動します | キャンバスなし – シングルアクション実行 | キャンバスなし – シングルアクション実行 | バッチキャンバス – すべてのプロファイルをまとめて処理 |
| **実行フロー** | 連続的なアクション、プロファイルはジャーニー全体の状態を維持 | オーディエンス全体への同時実行 | API呼び出しごとに即座に実行 | アクティビティとトランジションを含むマルチステップのバッチワークフロー |
| **入口メカニズム** | イベント、オーディエンス、選定、ビジネスイベント | 手動でのアクティブ化とスケジュール | 外部システムからのAPI コール | バッチワークフローのスケジュール済み実行 |
| **データモデル** | リアルタイムプロファイル + イベントデータ | Experience Platformオーディエンスからのプロファイルデータ | オプションのプロファイルルックアップを使用したAPI ペイロードデータ | 複数のエンティティの関係データ（プロファイル、商品、店舗、予約） |
| **セグメント化** | 事前定義済みのオーディエンス + リアルタイム条件 | Experience Platformの事前定義済みのオーディエンス | ペイロード主導のターゲティング（スケジュール型オーディエンスなし） | キャンバス内で作成されたオンデマンドオーディエンスと正確なカウント |
| **プロファイル処理** | 個人、リアルタイム（イベントが発生した場合） | バッチ（全て一度） | API呼び出しごとに、ペイロード駆動型 | バッチ、マルチエンティティのサポート |
| **Personalization** | リアルタイムのコンテキストデータ + プロファイル属性 | プロファイル属性 | ペイロードデータ + オプションのプロファイル属性 | 正確なターゲティングのためのマルチエンティティデータ |
| **複雑さ** | 分岐、待機時間、条件を使用したマルチステップ | 単一のアクションまたはシンプルなワークフロー | ペイロードマッピングによる単一アクション | セグメント化、エンリッチメント、分割によるマルチステップのバッチワークフロー |
| **最適** | カスタマーライフサイクル、オンボーディング、カート放棄 | プロモーションキャンペーン、ニュースレター、お知らせ | 注文確認、配送アラート、パスワードリセット | 複雑なシーズンキャンペーン、マルチステップのプロモーション、製品リリース |
| **タイミング** | 公開したら常にアクティブな状態で継続 | 予定開始日/終了日 | API経由のオンデマンドイベント駆動型 | スケジュールに従ったバッチ実行 |
| **状態の管理** | リアルタイムのアクションに対して顧客の状態を維持 | ステートレス実行 | 呼び出しごとのステートレス実行 | ワークテーブルを使用したバッチ処理 |
| **使用日時** | リアルタイムの意思決定ロジックにより、複数の顧客接点が必要 | 特定の時点でのオーディエンスへのシンプルなメッセージ | 外部システムは、メッセージを即座にトリガーする必要があります | 複雑なセグメンテーション、マルチエンティティデータ、正確な事前送信数が必要 |
| **一意の機能** | リアルタイムの反応、待機アクティビティ、プロファイルベースのペーシング | スケジューリング、オーディエンスのターゲティング、レート管理 | API ペイロードマッピング、システム間トリガー | 関係データセット，マルチエンティティセグメンテーション，正確なカウント，マルチレベルの送信 |

## 決定ガイド {#decision-guide}

このデジジョンツリーに従って、適切なアプローチを選択してください。 多くの企業は、複数のタイプを利用しており、各ユースケースに最適なものを選択しましょう。

### ステップ 1：何はあなたの実行要件？

**顧客の行動に対するリアルタイムの個別の反応は？**
→ **ジャーニーを使用**
* プロファイルは自分のペースで移動する必要があります
* 行動に基づく条件付きロジック
* リアルタイムのコンテキストが重要です

**スケジュールされた時間にオーディエンスにメッセージを簡単に配信できますか？**
→ **アクションキャンペーンを使用**
* すべてのプロファイルが同時にメッセージを受信する
* スケジュール済みまたは定期的な送信
* 複雑なマルチステップロジックは必要ありません

**外部システムによって即座にメッセージがトリガーされますか？**
→ **API トリガーのキャンペーンを使用**
* API呼び出しを介してオンデマンドでトリガー
* ペイロード主導のパーソナライゼーション
* 複雑なマルチステップロジックは必要ありません

**高度なセグメンテーションを使用した複雑なバッチワークフロー？**
→ **オーケストレーションされたキャンペーンを使用**
* 複数のエンティティのデータが必要（商品、店舗、予約）
* 正確な事前送信数を必要とする
* 分割とエンリッチメントによるマルチステップのバッチ処理

### ステップ 2：選択の検証

| お客様のニーズ | 推奨されるアプローチ | なぜ |
|-----------|---------------------|-----|
| マルチステップのオンボーディングで新規顧客を歓迎 | ジャーニー | リアルタイム入力、複数の顧客接点、条件付きパス |
| 購読者に毎月ニュースレターを送る | アクションキャンペーン | オーディエンスへのシンプルなスケジュール済みメッセージ |
| リマインダーシーケンスを使用したカートの放棄 | ジャーニー | リアルタイムのトリガー、待ち時間、条件付きフォローアップ |
| すべてのお客様へのプロモーションのお知らせ | アクションキャンペーン | 1回限りのメッセージ、即時配信 |
| 行動にもとづいて非アクティブユーザーをリエンゲージ | ジャーニー | オーディエンスの選定、パーソナライズされたパスによってトリガー |
| ビジネスイベントによってトリガーされるFlash セール | ジャーニー（ビジネスイベント） | 複数の顧客に影響を与えるリアルタイムのトリガー |
| 商品カタログ統合機能による季節ごとのプロモーション | キャンペーンの編成 | 複数のエンティティを含むデータ、複雑なセグメンテーション、正確な数 |
| API トリガートランザクションメッセージ | API トリガーによるキャンペーン | 外部システムトリガー、即時デリバリー |
| 予約ごとのマルチレベル送信 | キャンペーンの編成 | 複数のエンティティとの関係、予約ごとに1つのメッセージ |

## 主な違い {#key-distinctions}

### ジャーニー: 1:1 リアルタイム オーケストレーション

**ユニークな点：**
* 各プロファイルは、顧客一人ひとりの状況とニーズを把握し
* プロファイルは自分のペースでエントリおよび進行します
* 行動やイベントにもとづくリアルタイムの意思決定
* 待ち時間のアクティビティにより、タイミングをパーソナライズ
* 条件分岐は、プロファイルごとに一意のパスを作成します
* 組み込みのアクティブリスニング：定義された期間にわたり何も実行しないことで、明示的なイベントだけでなく、次のステップをトリガーにすることもできます。 [待機アクティビティについて説明](../building-journeys/wait-activity.md)
* 頻度の上限設定：顧客がジャーニーにエントリしたり、ジャーニーからメッセージを受信したりできる頻度を制御します。 [&#x200B; ジャーニーの上限について説明します](../conflict-prioritization/journey-capping.md)
* オーディエンスの割合による分割 – プロファイルをランダムな割合ベースのグループに分割し、ジャーニーパス全体でA/B実験を実施できます。 [&#x200B; パーセンテージ分割について説明](../building-journeys/condition-activity.md)
* テストモード：ライブ公開前に、テストプロファイルを使用してジャーニーロジックとメッセージ配信を検証します。 [&#x200B; テストモードについて学ぶ](../building-journeys/testing-the-journey.md)

**フローの例：**

```
Customer A: Abandoned cart → Wait 2 hours → No purchase? → Send reminder → Purchased? → End
Customer B: Abandoned cart → Wait 2 hours → Already purchased → End immediately
```

各顧客は、行動にもとづいて独自のジャーニータイムラインを体験します。

[ジャーニーについて詳しく見る](../building-journeys/journey.md)

### キャンペーン：シンプルなバッチまたはトリガー配信

**ユニークな点：**
* すべてのプロファイルが同じように同時に処理されます
* ステートレス実行 – コンテキストが維持されない
* シンプルなスケジューリングまたはAPI トリガー
* 放送通信に最適

**フローの例：**

```
Monday 9 AM → Send newsletter to 100,000 subscribers → All receive simultaneously
```

全員が同時に同じメッセージを受け取ることができます。

**種類：**
* **アクションキャンペーン**: オーディエンスへのスケジュールされた配信（1回限りまたは繰り返し）
* **API トリガーキャンペーン**: ペイロードデータを使用したAPI呼び出しによってトリガーされるオンデマンド配信

[キャンペーンの詳細](../campaigns/get-started-with-campaigns.md)

### オーケストレーションされたキャンペーン：バッチキャンバスワークフロー

**ユニークな点：**
* アクティビティとトランジションを含むバッチキャンバス（ジャーニーキャンバスと同様ですが、バッチ指向です）
* 複数のエンティティを統合したリレーショナルデータのサポート（プロファイル+商品+店舗+予約）
* キャンバス内でのオンデマンドオーディエンスの構築
* 送信前の正確なカウント（送信前の表示）
* マルチレベルの送信（エンティティごとに1つのメッセージ（例：予約ごとに）
* すべてのプロファイルを一括処理

**フローの例：**

```
Query customers → Filter by purchase history → Split by region → 
Enrich with product data → Build segments → Send personalized offers → All in one batch execution
```

ワークフローの複雑さとキャンペーンの一括実行の組み合わせ。

[オーケストレーションされたキャンペーンについて詳しく見る](../orchestrated/gs-orchestrated-campaigns.md)

## 事例 {#use-cases}

### ジャーニーユースケース

* **買い物かごの放棄の回復**: カート追加イベントによってトリガーされました。チェックアウトを待機し、購入しない場合はリマインダーを送信します
* **顧客オンボーディング**：プロファイルデータに基づいてパーソナライズされたコンテンツを含む、マルチステップのウェルカムシリーズ
* **ロイヤルティ階層のアップグレード**：お客様が新しい階層に到達したときにトリガーされます。お祝いと特典を送信します
* **誕生日キャンペーン**：誕生日に基づくエントリ、パーソナライズされたオファー
* **リエンゲージメント**：オーディエンスの選定（非アクティブ）、プログレッシブアウトリーチによってトリガーされる

### キャンペーンのユースケース（アクションとAPI トリガー）

**アクションキャンペーン：**
* **月次ニュースレター**：購読者セグメントへのバッチ配信をスケジュールしました
* **プロモーションのお知らせ**：ターゲットオーディエンスに対する時間制限のあるオファー
* **製品の発売**：すべての顧客に向けて調整されたお知らせ
* **季節の挨拶**：特定の日付に対するホリデーメッセージ

**API トリガーのキャンペーン：**
* **注文確認**：購入後にe コマースシステムによってトリガーされる
* **配送通知**：ロジスティクスシステムによってトリガーされます
* **アカウントアラート**：不正検出システムによってトリガーされました
* **パスワードリセット**：アプリケーションのユーザーアクションによってトリガーされます

### キャンペーンのユースケースを連携

* **カタログ統合による季節プロモーション**：商品カタログのクエリ、対象顧客の特定、環境設定によるセグメント化、パーソナライズされた商品レコメンデーションの送信
* **店舗固有のキャンペーン**：店舗の在庫データを使用して、特定の店舗の近くにいる顧客をターゲットにします
* **複数予約のコミュニケーション**：予約ごとに1つのメッセージを送信（ホテル予約、フライト予約）
* **複雑なセグメントオーケストレーション**：複数のデータソースからエンリッチメントを得て、段階的にオーディエンスを構築します
* **送信前の検証**：主要なキャンペーンを開始する前に正確な受信者数を取得します

## よくある質問 {#common-questions}

+++ マーケティング戦略でジャーニーとキャンペーンを組み合わせることはできますか？

はい。 多くの企業では、次の4つのアプローチをすべて、さまざまなシナリオで使用しています。

* 行動によるリアルタイムのエンゲージメントに関する&#x200B;**ジャーニー**
* スケジュールされたブロードキャスト通信の&#x200B;**アクションキャンペーン**
* トランザクションメッセージ用の&#x200B;**API トリガーキャンペーン**
* 複雑でデータ集約的なバッチキャンペーン用に&#x200B;**キャンペーンを**&#x200B;編成

すべてを無理なく進めるのではなく、各ユースケースに適したツールを使用する。

+++

+++ キャンペーンをジャーニーに変換することはできますか？その逆もできますか？

いいえ、エクスペリエンスを適切な形式で再構築する必要があります。 ただし、コンテンツ、オーディエンス、ロジックの概念は再利用できます。

+++

+++ どのアプローチが構築が簡単ですか？

アクションキャンペーンは、通常、最も単純なキャンペーン（オーディエンスに対するメッセージが1つ）で、API トリガーによるキャンペーン、ジャーニー（マルチステップロジックを使用してより複雑）、オーケストレーションされたキャンペーン（キャンバスワークフローとマルチエンティティの機能により最も複雑なキャンペーン）が続きます。

+++

+++ 大規模なオーディエンスに対応できる拡張性？

4つの機能はすべて、適切に拡張できます。適切な選択肢は、パターンによって異なります。

* **オーディエンスの読み取りジャーニー**&#x200B;と&#x200B;**アクションキャンペーン**&#x200B;は、大規模なバッチオーディエンス（1つのメッセージまたは一度に多くのプロファイルに送信）に最適化されています。
* **オーケストレーションされたキャンペーン**&#x200B;は、大規模なデータセットと複数のエンティティ データを使用した複雑なセグメンテーションに優れています。
* **単一（イベントベース）ジャーニー**&#x200B;は、イベントが発生するとプロファイルを個別に処理するので、スケールはイベントのボリュームとスループットに依存します。

+++

+++ ジャーニーやキャンペーンで同じオーディエンスを使用できますか？

はい。 [!DNL Adobe Experience Platform]で作成されたオーディエンスは、ジャーニー、アクションキャンペーン、オーケストレーションキャンペーンで使用できます（キャンバスでオーディエンスロジックをオンデマンドで構築することもできます）。 API トリガーによるキャンペーンはペイロード駆動型で、同じように事前定義済みのオーディエンスを使用することはありません。

+++
